# کافه‌منو — مستند کامل قابلیت‌ها

این فایل شرح کاملی از تمام بخش‌ها و قابلیت‌های نرم‌افزار «کافه‌منو» است: یک سیستم مدیریت کامل کافه/رستوران خودمیزبان (self-hosted) — از منوی دیجیتال و سفارش‌گیری گرفته تا POS، انبارداری، وفاداری مشتری، شیفت و صندوق، فاکتور و چاپ حرارتی — ساخته‌شده با Laravel 12. هر بخش دقیقاً بر اساس کد واقعی پروژه نوشته شده، نه توضیح کلی یا آرمانی.

## ۱. معماری کلی

- **بک‌اند:** Laravel 12 (PHP 8.2 تا 8.5)
- **دیتابیس:** MySQL 8+ یا MariaDB 10.6+
- **فرانت‌اند:** Blade + Tailwind CSS 4 + جاوااسکریپت خالص (بدون Vue/React/Alpine/Livewire/Inertia — طبق تصمیم معماری پروژه)
- **بلادرنگ (Real-time):** Laravel Reverb (سرور وب‌سوکت خودِ Laravel، سازگار با پروتکل Pusher)
- **صف کارها (Queue):** درایور `database` — نیازی به Redis ندارد (کارهایی مثل چاپ حرارتی و اعلان‌ها از همین صف رد می‌شوند)
- **پول:** همه‌جا عدد صحیح (integer) در کوچک‌ترین واحد پول ذخیره می‌شود، هرگز اعشاری — تا خطای گرد کردن رخ ندهد.
- **مقادیر انبار:** با دقت اعشاری ثابت (`decimal(14,4)`) و از طریق یک کلاس کمکی اختصاصی (شبیه به کلاس پول ولی برای موجودی) محاسبه می‌شوند — نه عملگرهای اعشاری معمول زبان که دچار خطای گرد کردن می‌شوند.
- **الگوی «عکس‌برداری تاریخی» (Snapshot):** در سفارش، فاکتور و آیتم‌های سفارش، نام/قیمت/مشخصات مشتری، محصول و افزودنی در لحظه‌ی ثبت به‌صورت جداگانه ذخیره می‌شود؛ تغییر بعدی رکورد اصلی (مثلاً تغییر نام مشتری یا قیمت محصول) هرگز سند مالی/سفارش قبلی را تغییر نمی‌دهد.
- **الگوی «دفترکل» (Ledger):** برای موجودی انبار، امتیاز وفاداری و گردش نقدی صندوق، هیچ عددی مستقیم تغییر نمی‌کند؛ هر تغییر یک ردیف جدید در یک جدول تنها-افزایشی (append-only) ثبت می‌کند و عدد نهایی (مثل موجودی فعلی یا امتیاز فعلی) فقط یک «کش» از جمع همان دفترکل است.
- **یک نصب = یک کسب‌وکار:** هیچ چندمستأجری (multi-tenancy) در کار نیست؛ هر نصب فقط برای یک کافه/رستوران است.
- **بدون وابستگی بیرونی غیرضروری:** حتی چاپ حرارتی (بخش ۱۷) بدون هیچ پکیج Composer اضافه‌ای، با پیاده‌سازی دستیِ پروتکل ESC/POS ساخته شده است.

## ۲. نقش‌ها و دسترسی‌ها (RBAC)

سیستم نقش و دسترسی کاملاً داخلی و سفارشی است (بدون پکیج بیرونی). هر کاربر دقیقاً یک نقش دارد؛ هر نقش مجموعه‌ای از دسترسی‌ها را در خود دارد.

### نقش‌های موجود

| نقش | جایگاه کلی |
|---|---|
| owner (مالک) | تمام دسترسی‌ها، بدون استثنا، از جمله مواردی که مدیر هم ندارد (مثل حاشیه سود، غیرفعال‌سازی اضطراری موجودی منفی) |
| manager (مدیر) | تقریباً همه‌چیز به‌جز مدیریت نقش‌ها و گزارش سود/حاشیه |
| cashier (صندوق‌دار) | سفارش‌گیری POS، پرداخت، مشتری، تخفیف/امتیاز، شیفت خودش، مشاهده/چاپ فاکتور |
| waiter (گارسون) | سفارش‌گیری POS، صدا زدن گارسون، مشتری، تخفیف/امتیاز، شیفت خودش، مشاهده فاکتور |
| kitchen (آشپزخانه) | فقط مشاهده سفارش و نمایشگر آشپزخانه؛ تغییر وضعیت سفارش |
| barista (باریستا) | مثل آشپزخانه |

### فهرست کامل دسترسی‌ها (Permissions)

| گروه | دسترسی | توضیح |
|---|---|---|
| dashboard | `dashboard.view` | مشاهده داشبورد |
| orders | `orders.view` / `orders.manage` / `orders.create` / `orders.split` | مشاهده سفارش / تغییر وضعیت و لغو / **ساخت سفارش از طرف مشتری (POS/گارسون)** / **تقسیم صورت‌حساب** |
| catalog | `categories.manage` / `products.manage` / `media.manage` | مدیریت دسته‌بندی، محصول و افزودنی‌ها (و نسخه/رسپی روی همین صفحات)، تصاویر |
| tables | `tables.manage` / `qr.manage` | مدیریت میز و بخش‌های میز / ساخت و دانلود QR |
| waiter_calls | `waiter_calls.view` / `waiter_calls.manage` | مشاهده / رسیدگی به صدا زدن گارسون |
| customers | `customers.view` / `customers.manage` | مشاهده مشتریان / مدیریت پروفایل و گروه‌بندی |
| discounts | `discounts.view` / `discounts.manage` / `discounts.apply` | مشاهده تخفیف/کمپین / **نویسندگی قوانین تخفیف** (سطح اعتماد بالاتر) / **اعمال تخفیف حین سفارش‌گیری** (سطح اعتماد پایین‌تر، جدا از نویسندگی) |
| loyalty | `loyalty.view` / `loyalty.manage` / `loyalty.redeem` | مشاهده قوانین/جوایز/موجودی امتیاز / نویسندگی قوانین و جوایز / استفاده از امتیاز مشتری برای یک سفارش |
| inventory | `inventory.view` / `inventory.manage` / `inventory.adjust` / `inventory.force_negative` | مشاهده انبار / مدیریت اقلام-واحد-دسته / ثبت تعدیل، ضایعات و انبارگردانی / **عبور اضطراری از موجودی منفی (فقط مالک)** |
| suppliers | `suppliers.manage` | مدیریت تأمین‌کنندگان |
| purchases | `purchases.view` / `purchases.manage` | مشاهده خرید / ثبت و دریافت خرید |
| shifts | `shifts.view_own` / `shifts.view_all` / `shifts.manage_all` | باز/بستن شیفت خود و ثبت گردش نقدی خود / مشاهده شیفت همه کارکنان / بستن اجباری شیفت دیگران |
| invoices | `invoices.view` / `invoices.manage` | مشاهده و چاپ فاکتور / صدور فاکتور و مدیریت قالب‌ها |
| printing | `printers.manage` | تنظیم چاپگرها و مسیر چاپ (فقط مالک/مدیر) |
| payments | `payments.view` / `payments.manage` / `payments.refund` | مشاهده پرداخت / ثبت و مدیریت پرداخت / **استرداد وجه** (سطح اعتماد جداگانه، بالاتر از ثبت پرداخت) |
| users | `users.manage` / `roles.manage` | مدیریت کارکنان / مدیریت نقش‌ها (فعلاً فقط مالک) |
| reports | `reports.view` / `reports.profit.view` | مشاهده گزارش‌ها / **مشاهده حاشیه سود و COGS (فقط مالک)** |
| system | `notifications.manage` / `audit.view` / `settings.manage` | مدیریت اعلان‌ها / مشاهده لاگ رویدادها / مدیریت تنظیمات |

هر کنترلر ادمین با استفاده از این دسترسی‌ها بررسی می‌کند که کاربر اجازه‌ی انجام آن عملیات را دارد یا نه — یعنی محدودیت دسترسی فقط در ظاهر منو نیست، در سمت سرور هم اجرا می‌شود. تفکیک `discounts.manage` از `discounts.apply` و `payments.manage` از `payments.refund` عمدی است: گارسون/صندوق‌دار می‌توانند تخفیف از قبل تعریف‌شده را اعمال یا امتیاز خرج کنند، اما نمی‌توانند قانون تخفیف جدید بسازند یا وجه برگردانند — این کارها دست مدیر/مالک است.

## ۳. ساختار پایگاه داده

جدول‌های اصلی، به‌ترتیب دامنه:

**هسته و کاربران**
- `users / roles / permissions / role_permission` — کاربران و سیستم دسترسی

**منو**
- `categories`, `products`, `product_option_groups`, `product_options`, `media`

**میز**
- `table_sections`, `tables`, `table_sessions`

**مشتری**
- `customer_groups`, `customers` — با `loyalty_points_balance` به‌عنوان کش موجودی امتیاز

**سفارش**
- `orders` (شامل `customer_id`، `waiter_id`، `source` یعنی سفارشِ خودِ مشتری یا POS کارمند، `status_changed_at`، `inventory_consumed_at`)
- `order_items`, `order_item_options`, `order_status_history`

**تخفیف و کمپین**
- `campaigns`, `discounts`, `discount_products`, `discount_categories`, `discount_customers`, `discount_customer_groups` (پیوت‌ها)، `discount_redemptions`

**وفاداری**
- `loyalty_rules`, `loyalty_rewards`, `loyalty_ledger_entries` (دفترکل تنها-افزایشی امتیاز)، `loyalty_redemptions`

**انبار**
- `inventory_units`, `inventory_categories`, `inventory_items`, `suppliers`, `purchases`, `purchase_items`, `stock_movements` (دفترکل تنها-افزایشی موجودی)، `stock_adjustments`+`stock_adjustment_items`, `stock_counts`+`stock_count_items`, `waste_records`, `purchase_returns`+`purchase_return_items`

**نسخه غذا**
- `recipe_items` (رابطه‌ی چندریختی به محصول یا آپشن محصول)

**شیفت و صندوق**
- `shifts`, `cash_movements`

**تقسیم صورت‌حساب**
- `bill_splits`, `bill_split_parts`, `bill_split_part_items`

**پرداخت و استرداد**
- `payments` (با `bill_split_part_id` اختیاری)، `refunds`

**فاکتور**
- `invoice_templates`, `invoices`, `invoice_line_items`

**چاپ**
- `printers`, `print_routes`, `print_jobs`

**زیرساخت**
- `waiter_calls`, `notifications`, `audit_logs`, `business_settings`, `system_settings`

نکته‌ی مهم: تمام مبالغ پولی همه‌جا به‌صورت عدد صحیح ذخیره می‌شوند؛ تمام مقادیر انبار با دقت ۴ رقم اعشار ثابت. هیچ عدد پولی یا مقدار انبار هرگز مستقیماً «آپدیت» نمی‌شود — همه از دفترکل مربوطه (`stock_movements`، `loyalty_ledger_entries`، `cash_movements`) قابل بازسازی هستند.

## ۴. مدیریت منو

### دسته‌بندی‌ها
نام، اسلاگ (لینک)، توضیح، ترتیب نمایش، فعال/غیرفعال، و امکان داشتن زیردسته (یک سطح). حذف دسته‌بندی‌ای که زیردسته یا محصول دارد مسدود است.

### محصولات
هر محصول شامل: نام، اسلاگ، توضیح، قیمت پایه، قیمت تخفیف‌خورده (اختیاری، همیشه باید کمتر از قیمت پایه باشد)، وضعیت «موجود بودن الان» (`is_available`) جدا از «فعال بودن در منو» (`is_active`)، و یک برچسب اختیاری: **جدید**، **محبوب** یا **ویژه**.

> از این نسخه به بعد، «موجود بودن» صرفاً یک کلید دستی نیست — اگر برای محصول نسخه‌ی مصرف مواد اولیه (رسپی، بخش ۱۱) تعریف شده باشد، هر بار فروخته‌شدنش موجودی واقعی انبار را کم می‌کند و در صورت کمبود موجودی، تأیید سفارش با خطا رد می‌شود.

### افزودنی‌های محصول (Option Groups)
برای هر محصول می‌توان گروه‌های افزودنی تعریف کرد (مثلاً «سایز» با انتخاب اجباری تک‌گزینه‌ای، یا «افزودنی‌ها» با انتخاب چندگزینه‌ای اختیاری). هر گزینه می‌تواند مبلغی به قیمت اضافه یا کم کند (مقدار منفی هم مجاز است). حداقل/حداکثر تعداد انتخاب برای هر گروه در سمت سرور هم بررسی می‌شود. هر آپشن هم می‌تواند نسخه‌ی مصرف مواد اولیه‌ی خودش را داشته باشد (مثلاً «شات اضافه» یک‌بار دیگر دانه قهوه مصرف می‌کند).

### تصاویر
هر محصول، دسته‌بندی، یا لوگوی کسب‌وکار می‌تواند تصویر داشته باشد. تصاویر آپلودی به‌صورت خودکار:
- در صورت بزرگ‌تر بودن از ۲۰۰۰ پیکسل، تغییر‌اندازه داده می‌شوند
- فشرده‌سازی می‌شوند (JPEG/WebP/PNG)
- جهت صحیح می‌گیرند (چرخش خودکار عکس‌های موبایل)
- اولین عکس آپلودی به‌صورت خودکار «تصویر اصلی» می‌شود و ترتیب نمایش قابل تنظیم است

## ۵. میزها و کد QR

### ساختار
میزها داخل «بخش‌های میز» (مثل سالن اصلی، بالکن، تراس) دسته‌بندی می‌شوند. هر میز یک ظرفیت، وضعیت (موجود / خارج از سرویس)، و یک **کد QR اختصاصی و غیرقابل‌حدس** دارد.

### مسیر کامل اسکن تا سفارش
۱. کارمند از پنل مدیریت، کد QR میز را چاپ می‌کند (روی خود میز می‌چسبد).
۲. مشتری کد را اسکن می‌کند → مرورگر مستقیم به منوی دیجیتال با میزِ تشخیص‌داده‌شده هدایت می‌شود.
۳. تمام صفحات بعدی (منو، جزئیات محصول، سبد خرید) می‌دانند مشتری سر کدام میز نشسته.
۴. هنگام ثبت سفارش، سرور دوباره بررسی می‌کند میز واقعاً فعال و موجود است — هرگز به داده‌ای که از مرورگر مشتری فرستاده شده اعتماد نمی‌کند.
۵. یک «جلسه‌ی میز» (Table Session) باز می‌شود یا در صورت وجود، همان جلسه‌ی باز فعلی استفاده می‌شود — همه‌ی سفارش‌های یک نشستن مشتری‌ها زیر یک جلسه جمع می‌شوند (برای صورت‌حساب مشترک).
۶. دکمه‌ی «صدا کردن گارسون» هم فقط بر اساس همین میزِ اسکن‌شده کار می‌کند.

کارمند هم می‌تواند مستقل از اسکن مشتری، از پنل POS (بخش ۷) همان میز را باز کرده و سفارش ثبت کند؛ در این حالت هر دو مسیر روی یک جلسه‌ی میز مشترک قرار می‌گیرند و سفارش‌هایشان با هم جمع می‌شود.

### مدیریت جلسه‌ی میز
از پنل ادمین می‌توان: جلسه را بست، به میز دیگری منتقل کرد (جابه‌جایی مهمان‌ها)، یا دو جلسه را با هم ادغام کرد (برای صورت‌حساب مشترک دو میز). انتقال/ادغام جلسه، ستون میزِ خودِ سفارش‌ها را هم هماهنگ می‌کند تا هرگز میزِ ثبت‌شده‌ی یک سفارش با میزِ جلسه‌اش ناهم‌خوان نماند.

### کد QR منوی عمومی
جدا از QR هر میز، یک کد QR برای «کل منو» هم وجود دارد (برای سفارش بیرون‌بر/تحویل حضوری بدون میز مشخص).

## ۶. مشتریان

مشتری یک موجودیت مستقل و درجه‌یک است، نه فقط یک نام روی سفارش.

### پروفایل مشتری
نام، شماره موبایل (اختیاری ولی یکتا)، ایمیل (اختیاری)، یادداشت، وضعیت (فعال/مسدود)، عضویت اختیاری در یک **گروه مشتریان** (مثلاً «مشتریان ویژه» — همان چیزی که موتور تخفیف می‌تواند برای اعمال تخفیف گروهی از آن استفاده کند)، و موجودی امتیاز وفاداری (بخش ۹).

### مهمان (Guest)
اگر سفارشی مشتری مشخصی نداشته باشد، به‌سادگی `customer_id` آن خالی می‌ماند — هیچ رکورد ساختگی «مهمان» ساخته نمی‌شود تا آمار و گزارش‌ها را مخدوش نکند. سفارش‌های عمومی (اسکن QR) هرگز به یک مشتری واقعی متصل نمی‌شوند مگر از طریق پنل POS.

### سابقه و آمار خرید
برای هر مشتری، تعداد سفارش، جمع مبلغ خرید، میانگین ارزش سفارش و تاریخ آخرین خرید همیشه **زنده از روی سفارش‌های واقعی محاسبه می‌شود**، نه یک عدد ذخیره‌شده که ممکن است با واقعیت فرق کند.

### سازگاری تاریخی
تغییر نام/شماره‌ی یک مشتری هرگز فاکتور یا سفارش قبلی او را عوض نمی‌کند — دقیقاً مثل بخش ۷، هر سفارش نام و شماره‌ی مشتری را در لحظه‌ی ثبت «عکس‌برداری» و ذخیره می‌کند؛ `customer_id` فقط یک ارجاع زنده‌ی اضافی است، نه منبع اصلی آن رکورد تاریخی.

هیچ حذف قطعی (hard delete) برای مشتری وجود ندارد — فقط غیرفعال‌سازی.

## ۷. جریان سفارش‌گیری

سیستم دو مسیر کاملاً مجزا برای ساخت سفارش دارد که هر دو از یک موتور قیمت‌گذاری مشترک (که تخفیف و امتیاز را هم اعمال می‌کند) عبور می‌کنند — یعنی هرگز بین سفارش مشتری و سفارش کارمند در محاسبه‌ی قیمت اختلافی پیش نمی‌آید.

### مسیر ۱ — سفارش عمومی (اسکن QR مشتری)
انواع سفارش: **صرف در محل** (dine_in، نیازمند اسکن میز)، **بیرون‌بر** (takeaway)، **دریافت حضوری** (pickup)، **ارسال** (delivery). هرکدام جداگانه از تنظیمات کسب‌وکار قابل فعال/غیرفعال است. این مسیر فقط تخفیف‌های خودکارِ واجدشرایط را اعمال می‌کند؛ انتخاب دستی تخفیف یا خرج امتیاز فقط از POS ممکن است.

### مسیر ۲ — پنل POS / گارسون (کارمند از طرف مشتری)
از پنل ادمین، بخش «POS» به کارمندِ دارای دسترسی `orders.create` اجازه می‌دهد:
- سالن و میز را انتخاب کند، یا برای فروش پیشخوان بدون میز («سفارش پیشخوانی») فقط نام و شماره یا یک مشتری ثبت‌شده وارد کند
- یک مشتری ثبت‌شده را به سفارش متصل کند (نام/شماره‌اش خودکار عکس‌برداری می‌شود)
- محصولات و افزودنی‌ها را مرور و اضافه کند، با یادداشت روی هر قلم
- تخفیف واجدشرایط را (در صورت داشتن `discounts.apply`) اعمال کند یا امتیاز وفاداری مشتری را (در صورت داشتن `loyalty.redeem`) خرج کند
- سفارش را ثبت کند — دقیقاً مثل مسیر عمومی، هیچ قیمتی از مرورگر پذیرفته نمی‌شود

اگر دو نفر (مثلاً هم مشتری با اسکن QR و هم گارسون از POS) به یک میز مراجعه کنند، هر دو روی همان جلسه‌ی باز میز قرار می‌گیرند.

### افزودن قلم به سفارش موجود
تا وقتی سفارش در وضعیت «در انتظار»، «تأییدشده» یا «در حال آماده‌سازی» باشد و یک فاکتور برایش صادر نشده باشد، می‌توان قلم جدید به آن اضافه کرد. سیستم کل سبد (اقلام قبلی + جدید) را دوباره از صفر از موتور قیمت‌گذاری رد می‌کند — نه فقط جمع را وصله می‌زند — تا شرط‌های تخفیف (مثل حداقل تعداد) با ترکیب جدید سبد هم درست بمانند. اگر یک جایزه‌ی وفاداری قبلاً روی همین سفارش خرج شده باشد یا فاکتور صادر شده باشد، افزودن قلم مسدود می‌شود (چون امتیاز خرج‌شده یا فاکتور صادرشده دیگر قابل بازمحاسبه‌ی بی‌خطر نیست).

### وضعیت‌های سفارش و مسیر مجاز تغییر
```
در انتظار (pending)     → تأییدشده، ردشده، لغوشده
تأییدشده (confirmed)    → در حال آماده‌سازی، لغوشده
در حال آماده‌سازی (preparing) → آماده، لغوشده
آماده (ready)           → تکمیل‌شده
تکمیل‌شده / لغوشده / ردشده → پایانی (غیرقابل تغییر)
```
هر تغییر وضعیت در تاریخچه ثبت می‌شود (چه کسی، چه زمانی، از کجا به کجا)، زمان دقیق تغییر جداگانه ذخیره می‌شود (برای تشخیص سفارش معطل‌مانده در نمایشگر آشپزخانه)، و به‌صورت لحظه‌ای هم به مشتری و هم به پنل ادمین اطلاع داده می‌شود. این ماشین حالت از ابتدای پروژه ثابت مانده — هیچ‌کدام از قابلیت‌های جدید (انبار، وفاداری، چاپ) وضعیت جدیدی به آن اضافه نکرده‌اند؛ همه به‌عنوان اثر جانبیِ همین گذارهای موجود اجرا می‌شوند:
- **تأیید سفارش (confirmed):** مواد اولیه‌ی رسپی هر قلم از انبار کم می‌شود (بخش ۱۱)؛ اگر موجودی کافی نباشد، خودِ تأیید با خطا رد می‌شود. دستور چاپ به آشپزخانه/بار هم همین‌جا صادر می‌شود (بخش ۱۷).
- **لغو (cancelled):** اگر مواد اولیه قبلاً کم شده بود، برگردانده می‌شود.
- **تکمیل (completed):** در صورت داشتن مشتری، امتیاز وفاداری طبق قوانین فعال محاسبه و اضافه می‌شود (بخش ۹).

### وضعیت پرداخت سفارش
جدا از وضعیت سفارش، وضعیت پرداخت (در انتظار / پرداخت‌شده / ناموفق / بازگشت‌داده‌شده / **بخشی بازگشت‌داده‌شده**) به‌صورت خودکار از روی مجموع پرداخت‌های موفقِ سفارش، منهای هر استرداد ثبت‌شده (بخش ۱۵)، محاسبه می‌شود.

### مراحل ثبت سفارش (پشت‌صحنه)
هنگام ثبت سفارش (در هر دو مسیر)، سرور:
- قیمت و در دسترس‌بودن هر محصول و هر افزودنی را دوباره از دیتابیس می‌خواند (هرگز به قیمتی که از مرورگر ارسال شده اعتماد نمی‌کند)
- تعداد انتخاب‌های هر گروه افزودنی را با محدودیت حداقل/حداکثرش می‌سنجد
- تخفیف‌های خودکار واجدشرایط را اعمال می‌کند (و در POS، تخفیف/امتیاز دستی‌انتخاب‌شده را هم روی همین جمع می‌نشاند)
- جمع کل، **بر مبنای مبلغ پس از تخفیف**، مالیات (در صورت فعال بودن) و عوارض خدمت (در صورت فعال بودن) را محاسبه می‌کند
- نام و قیمت هر قلم را در همان لحظه «عکس‌برداری» و ذخیره می‌کند — یعنی تغییر بعدی قیمت محصول در منو، سفارش‌های قبلی را تغییر نمی‌دهد
- برای مشتریانی که پرداخت نقدی هنگام دریافت حضوری انتخاب کرده‌اند، یک رکورد پرداخت «در انتظار» می‌سازد
- به همه‌ی کارکنانی که دسترسی مشاهده‌ی سفارش دارند اعلان لحظه‌ای می‌فرستد

## ۸. موتور تخفیف

یک موتور تخفیف واقعی و قانون‌محور — نه یک درصد ثابت هاردکد در مدل سفارش.

### انواع تخفیف
درصدی، مبلغ ثابت، تخفیف روی یک قلم خاص، نیم‌بها، بخر-X-ببر-Y، و کالای رایگان. تخفیف «کالای رایگان»/«بخر-X-ببر-Y» یک قلم سفارش **واقعی** با قیمت عادی می‌سازد و بعد ۱۰۰٪ همان قلم را تخفیف می‌دهد — یعنی در گزارش فروش و مصرف انبار، دقیقاً به همان اندازه که واقعاً هدیه داده شده، حساب و از انبار کم می‌شود؛ چیزی از هیچ اختراع نمی‌شود.

### شرایط اعمال (قابل ترکیب)
محصول یا دسته‌بندی خاص، مشتری یا گروه مشتری خاص، روز هفته، بازه‌ی تاریخ، بازه‌ی ساعت، حداقل مبلغ سفارش، حداقل تعداد قلم.

### قوانین دیگر
هر تخفیف اولویت دارد (برای تعیین برنده در صورت تداخل)، قابل ترکیب‌شدن با تخفیف‌های دیگر یا نه، فعال/غیرفعال، تاریخ شروع/پایان، و سقف استفاده (کلی و به‌ازای هر مشتری) — که همزمانی مصرفِ آخرین سهمیه‌ی یک تخفیف محدود با قفل پایگاه‌داده کنترل می‌شود تا دو نفر همزمان نتوانند از یک سهمیه‌ی آخر، دوبار استفاده کنند.

هر بار که یک تخفیف روی سفارشی اعمال شود، یک رکورد در «تاریخچه‌ی تخفیف مشتری» ثبت می‌شود (چه تخفیفی، چقدر، روی کدام قلم) — همان چیزی که هم در پروفایل مشتری و هم در گزارش‌ها قابل مشاهده است. تخفیف‌ها می‌توانند داخل یک «کمپین» (مثلاً «جشنواره زمستانه») دسته‌بندی شوند.

جمع کل سفارش هرگز منفی نمی‌شود — هر تخفیفِ سطح-قلم به سقف مبلغ همان قلم، و هر تخفیفِ سطح-سفارش به سقف باقی‌مانده‌ی جمع کل محدود می‌شود.

## ۹. باشگاه مشتریان و امتیاز وفاداری

سیستم وفاداری بر پایه‌ی **امتیاز غیرپولی** است، نه اعتبار ریالی — امتیاز هرگز یک روش پرداخت یا رکورد مالی مستقیم نیست؛ فقط زمان خرج‌شدن، به یک اثر تخفیفی روی سفارش (یا یک کالای رایگان) تبدیل می‌شود.

### کسب امتیاز
دو نوع قانونِ فعال هم‌زمان ممکن است:
- **آستانه‌ی خرج:** مثلاً هر خرید بالای ۱۰۰,۰۰۰ تومان، ۵۰ امتیاز
- **بخر-X-ببر-امتیاز-Y:** مثلاً هر ۲ قلم سفارش، ۱۰ امتیاز جایزه

امتیاز فقط زمانی که سفارش به وضعیت «تکمیل‌شده» می‌رسد و سفارش به یک مشتری متصل است محاسبه می‌شود — چون این وضعیت پایانی و غیرقابل‌برگشت است، امکان محاسبه‌ی دوباره یا فراموش‌شدن وجود ندارد.

### خرج امتیاز
از پنل POS، کارمند دارای `loyalty.redeem` می‌تواند یکی از جوایز تعریف‌شده را برای مشتریِ آن سفارش خرج کند: تخفیف مبلغ ثابت، تخفیف درصدی، یا یک محصول رایگان. مبلغ حاصل هرگز از باقی‌مانده‌ی قابل‌پرداخت سفارش بیشتر نمی‌شود. اگر موجودی امتیاز مشتری کافی نباشد، خرج امتیاز رد می‌شود.

### دفترکل امتیاز
هر افزایش یا کاهش امتیاز (کسب، خرج، انقضا، تعدیل دستی) یک ردیف در دفترکلِ تنها-افزایشیِ امتیاز ثبت می‌کند؛ موجودی فعلی مشتری فقط یک کش از همین دفترکل است و هرگز مستقیماً دستکاری نمی‌شود، پس همیشه قابل ردیابی و حسابرسی است.

## ۱۰. انبارداری

یک سیستم انبارداری واقعی — نه فقط کلید «موجود/ناموجود» روی محصول.

### واحد، دسته‌بندی و کالا
واحدهای اندازه‌گیری (گرم/کیلوگرم، میلی‌لیتر/لیتر، عدد) با ضریب تبدیل به یک واحد پایه‌ی هر نوع؛ تبدیل فقط بین واحدهای هم‌نوع مجاز است (مثلاً گرم به میلی‌لیتر بدون چگالی امکان‌پذیر نیست و رد می‌شود). هر کالای انبار (مثل «دانه قهوه» یا «شیر») یک دسته‌بندی، یک واحد پایه، حداقل/حداکثر موجودی، و میانگین قیمت تمام‌شده (بر مبنای واحد پایه‌اش) دارد.

### تأمین‌کننده و خرید
تأمین‌کنندگان با اطلاعات تماس؛ برای هر خرید یک یا چند قلم (کالا + واحد خریدِ همان قلم + تعداد + قیمت واحد)، با شماره‌ی خرید یکتا و وضعیت (پیش‌نویس / سفارش داده‌شده / بخشی دریافت‌شده / دریافت‌شده / لغوشده) و وضعیت پرداخت جدا (پرداخت‌نشده/بخشی/کامل).

### دریافت خرید = تنها راه ورود موجودی
دریافت یک خرید (کامل یا بخشی) تنها راهی است که اقلام آن به موجودی واقعی تبدیل می‌شوند. اگر خرید در واحدی غیر از واحد پایه‌ی کالا ثبت شده باشد (مثلاً خرید بر حسب کیلوگرم برای کالایی که بر حسب گرم ردیابی می‌شود)، هم مقدار و هم قیمت واحد به‌درستی به واحد پایه تبدیل می‌شوند تا میانگین قیمت تمام‌شده هرگز به‌اشتباه هزار برابر یا یک‌هزارم محاسبه نشود.

### دفترکل موجودی (منبع حقیقت)
هیچ عملیاتی مستقیماً `current_stock` را تغییر نمی‌دهد — هر افزایش یا کاهش (دریافت خرید، فروش، لغو فروش، تعدیل افزایشی/کاهشی، ضایعات، مرجوعی به تأمین‌کننده، مرجوعی از مشتری، موجودی ابتدایی، اصلاح انبارگردانی) یک ردیف در دفترکل تنها-افزایشیِ حرکات انبار ثبت می‌کند؛ موجودی فعلی فقط جمع همین ردیف‌هاست. تلاش برای بردن موجودی به زیر صفر همیشه رد می‌شود، مگر با دسترسی اضطراری مخصوص مالک (`inventory.force_negative`).

### تعدیل، ضایعات، انبارگردانی، مرجوعی
تعدیل دستی موجودی (با دلیل)، ثبت ضایعات (با قیمت پیش‌فرض از میانگین قیمت تمام‌شده)، فرایند کامل انبارگردانی (شروع → ثبت شمارش واقعی → تکمیل، که در لحظه‌ی تکمیل به‌صورت غیرقابل‌بازگشت یک «اصلاح» برای هر اختلاف می‌سازد)، و ثبت مرجوعی به تأمین‌کننده.

### هشدار کمبود موجودی
یک فرمان زمان‌بندی‌شده (هر ساعت) موجودی همه‌ی کالاها را نسبت به حداقل‌شان می‌سنجد و به هر کاربر با دسترسی `inventory.view` اعلان لحظه‌ای می‌فرستد؛ برای جلوگیری از سیل اعلان تکراری، بعد از یک بار هشدار، تا وقتی موجودی دوباره بالای حد تعریف‌شده نرود، دوباره هشدار نمی‌دهد.

## ۱۱. نسخه غذا / فرمول ساخت (Recipe – BOM)

هر محصول (یا حتی هر آپشنِ یک محصول، مثل «شات اضافه») می‌تواند فهرستی از کالاهای انبار مصرفی‌اش را داشته باشد — مثلاً «لاته» به‌ازای هر عدد فروش، ۱۸ گرم دانه قهوه و ۲۰۰ میلی‌لیتر شیر مصرف می‌کند.

### مصرف خودکار
وقتی سفارش تأیید می‌شود (وضعیت confirmed، بخش ۷)، برای هر قلم سفارش، نسخه‌ی **فعلیِ** محصول/آپشن (نه نسخه‌ی زمان ثبت سفارش) خوانده، در تعداد همان قلم ضرب، و به واحد پایه‌ی هر کالا تبدیل می‌شود؛ سپس یک حرکت «مصرف فروش» در دفترکل انبار ثبت می‌شود. اگر یک محصول اصلاً نسخه‌ای نداشته باشد، بدون خطا از کنارش رد می‌شود (یعنی سیستم رسپی کاملاً اختیاری است).

### اتمی بودن و بازگشت‌پذیری
همه‌ی کسر مواد یک سفارش در یک تراکنش واحد انجام می‌شود — اگر کمبود موجودی یک ماده باعث شکست شود، حتی مواد قبلاً کسرشده‌ی همان سفارش هم برمی‌گردد و خودِ تأیید سفارش با خطا رد می‌شود (یعنی کارمند سفارشی را که آشپزخانه واقعاً نمی‌تواند تأمین کند، تأیید نمی‌کند). اگر سفارشی بعد از مصرف مواد لغو شود، همان مقدار به‌صورت خودکار به انبار برمی‌گردد.

---

## ۱۲. نمایشگر آشپزخانه (Kitchen Display)

یک KDS عملی برای نقش‌های آشپزخانه/باریستا (که هیچ دسترسی مدیریتی نامرتبطی ندارند):

- سفارش‌های فعال (تأییدشده، در حال آماده‌سازی، آماده) در ستون‌های جدا بر اساس وضعیت
- برای هر سفارش: شماره، میز، اقلام، افزودنی‌ها، یادداشت، زمان سپری‌شده
- **سفارش معطل‌مانده:** اگر سفارشی بیش از یک آستانه‌ی زمانی قابل‌تنظیم (پیش‌فرض ۱۵ دقیقه) در همان وضعیت مانده باشد، به‌صورت بصری علامت‌گذاری می‌شود — این وضعیت محاسبه‌شده است، نه یک فیلد ذخیره‌شده
- دکمه‌های تغییر وضعیت مستقیماً همان مسیر تغییر وضعیت معمولی سفارش را صدا می‌زنند (بخش ۷) — هیچ منطق موازی یا جداگانه‌ای ندارد
- سفارش‌های تکمیل‌شده در نمایشگر دیده نمی‌شوند؛ به‌روزرسانی هم لحظه‌ای است (بخش ۱۹)

---

## ۱۳. شیفت و صندوق نقدی

هر کارمند می‌تواند شیفت کاری خودش را باز/بسته کند؛ در هر لحظه هر کاربر حداکثر یک شیفت باز دارد.

### باز کردن شیفت
مبلغ نقد ابتدای شیفت (تنخواه/ته‌صندوق) ثبت می‌شود.

### گردش نقدی حین شیفت
هر ورود/خروج دستیِ نقد (با دلیل الزامی)، و همچنین **هر پرداخت نقدیِ موفق حین همان شیفت به‌صورت خودکار** به‌عنوان یک ردیف «فروش» در دفترکل گردش نقدی همان شیفت ثبت می‌شود — این اتصال کاملاً اختیاری است: اگر کارمندی اصلاً شیفت باز نداشته باشد، رفتار پرداخت‌ها بدون هیچ تغییری مثل قبل کار می‌کند.

### بستن شیفت
مبلغ نقدِ مورد انتظار به‌صورت خودکار از «نقد ابتدای شیفت + مجموع گردش‌های نقدی» محاسبه می‌شود؛ کارمند مبلغ واقعی شمرده‌شده را وارد می‌کند و اختلاف (کسری/اضافه) ثبت می‌شود.

**قانون مهم:** اگر هنگام بستن شیفت، جلسه‌های میزِ باز و پرداخت‌نشده وجود داشته باشد، سیستم فقط یک **هشدار نرم** (تعداد آن‌ها) نشان می‌دهد و اجازه‌ی بستن را می‌دهد — هرگز بستن شیفت را قفل نمی‌کند.

---

## ۱۴. تقسیم صورت‌حساب (Split Bill)

یک سفارش/میز می‌تواند به چند بخش پرداخت جداگانه تقسیم شود:

- **بر اساس قلم:** هر بخش، مجموعه‌ای مشخص از اقلام سفارش را به عهده می‌گیرد (مناسب برای «هرکس حساب خودش را بدهد»)
- **مساوی:** جمع کل به تعداد نفرات مساوی تقسیم می‌شود
- **بر اساس مبلغ دلخواه:** مبلغ هر بخش دستی وارد می‌شود، به شرط آنکه مجموع دقیقاً برابر جمع کل باشد

تخفیف/مالیات/عوارض خدمتِ سطح-سفارش با روش «بزرگ‌ترین باقیمانده» بین بخش‌ها توزیع می‌شود تا مجموع دقیقاً با جمع کل سفارش برابر باشد (نه یک ریال کم یا زیاد).

**تضمین در سطح دیتابیس، نه فقط منطق برنامه:** هر قلم سفارش حداکثر می‌تواند به یک بخش تعلق بگیرد — این محدودیت با یک قید یکتای دیتابیسی اجرا می‌شود، یعنی حتی یک باگ احتمالی در کد هم نمی‌تواند باعث دو بار حساب شدن یک قلم شود. هر بخش پرداختش را جداگانه می‌پذیرد (از همان مسیر معمول ثبت پرداخت) و به‌محض تسویه‌ی همه‌ی بخش‌ها، کل تقسیم به‌صورت خودکار «تسویه‌شده» علامت می‌خورد.

---

## ۱۵. پرداخت‌ها و استرداد وجه

### روش‌های پرداخت
- **نقدی** و **کارت‌خوان** — ثبت دستی توسط کارمند
- **پرداخت در محل** (pay_later)
- **آنلاین** — از طریق درگاه‌های پرداخت ایرانی (زرین‌پال، زیبال، ملت)

یک سفارش می‌تواند چند پرداخت داشته باشد (مثلاً تقسیم صورت‌حساب)؛ وضعیت پرداخت کاملاً مستقل از وضعیت سفارش محاسبه می‌شود.

### امنیت و جلوگیری از پرداخت تکراری
- اگر مشتری دو بار روی «پرداخت آنلاین» بزند، پرداخت قبلیِ نیمه‌کاره خودکار لغو می‌شود تا دوبار حساب نشود.
- وقتی درگاه نتیجه‌ی پرداخت را برمی‌گرداند، سیستم هرگز فقط به همان پیام برگشتی اعتماد نمی‌کند — همیشه یک استعلام مستقیم و جدید با خود درگاه انجام می‌دهد.
- اگر همان نتیجه دوبار برگردد، سیستم آن را تشخیص می‌دهد و دوباره حساب نمی‌کند.
- بیشتر پرداخت از مبلغ واقعی سفارش امکان‌پذیر نیست.

### استرداد وجه (Refund)
استرداد کامل یا جزئی، فقط برای پرداخت‌های «پرداخت‌شده»، توسط کاربرانی که دسترسی جداگانه‌ی `payments.refund` دارند (سطح اعتماد بالاتر از ثبت پرداخت معمولی). هر استرداد:
- هرگز پرداخت اصلی را حذف یا تغییر نمی‌دهد — یک رکورد استرداد جدید و مستقل ثبت می‌شود، و تاریخچه‌ی کامل پرداخت اصلی دست‌نخورده می‌ماند
- نمی‌تواند از «مبلغ قابل‌استرداد» (مبلغ پرداخت منهای استردادهای قبلی) بیشتر باشد
- وضعیت پرداخت سفارش را به «بازگشت‌داده‌شده» یا «بخشی بازگشت‌داده‌شده» به‌روزرسانی می‌کند
- اگر روش استرداد نقدی باشد و کارمند شیفت باز داشته باشد، یک گردش نقدی منفی در صندوق همان شیفت ثبت می‌کند
- اگر پرداختِ مربوطه بخشی از یک تقسیم صورت‌حساب باشد، وضعیت همان بخش دوباره همگام می‌شود

**محدودیت آگاهانه:** برای درگاه‌های آنلاین، این سیستم تماس مستقیم با API بازگشت وجهِ درگاه را انجام نمی‌دهد (هیچ‌کدام از سه درگاه متصل‌شده چنین قابلیتی در ادغام فعلی ندارند) — استرداد آنلاین فقط جنبه‌ی حسابداری/دفترداری دارد و بازگشت واقعی مبلغ باید از پنل خودِ درگاه انجام شود.

## ۱۶. فاکتور و قالب فاکتور

فاکتور یک سند مالی رسمی و **دستی‌صادرشونده** است (نه خودکار به‌محض پرداخت — چون یک پرداخت جزئی یا تقسیم‌شده، لحظه‌ی مشخصی برای «همین الان فاکتور بزن» ندارد؛ تصمیمش با کارمند است).

### محتوا
شماره فاکتور یکتا، تاریخ و ساعت، نام و شماره‌ی مشتری، میز، گارسون، اقلام با تعداد و قیمت واحد، تخفیف، مالیات، و جمع کل — همه‌چیز **دوباره از روی خودِ سفارش عکس‌برداری** می‌شود (نه فقط ارجاع به آن)، تا فاکتور صادرشده حتی اگر سفارش/مشتری/محصول بعداً تغییر کند، هرگز عوض نشود.

### قالب‌ها
چند قالب فاکتور قابل تعریف است (اندازه‌ی کاغذ A4 یا حرارتی ۵۸/۸۰ میلی‌متری، نمایش یا عدم نمایش لوگو، متن سربرگ/پانویس سفارشی)؛ همیشه دقیقاً یک قالب «پیش‌فرض» فعال است.

### صدور یک‌باره
تولید فاکتور برای یک سفارش، ایمن‌به‌تکرار (idempotent) است — درخواست دوباره‌ی «صدور فاکتور» برای همان سفارش، فاکتور تکراری نمی‌سازد؛ همان فاکتور قبلی را برمی‌گرداند.

## ۱۷. چاپ حرارتی (ESC/POS)

اتصال **واقعی** به چاپگر حرارتی — نه فقط چاپ مرورگر به PDF.

### اتصال
چاپگر شبکه‌ای (روی پورت استاندارد ۹۱۰۰) یا چاپگر USB. برای هر چاپگر: نام، نوع اتصال، آدرس/پورت یا مسیر دستگاه، عرض کاغذ (۵۸ یا ۸۰ میلی‌متر).

### پیاده‌سازی پروتکل
بدون افزودن هیچ پکیج بیرونی، پروتکل ESC/POS به‌صورت دستی و مستقیم پیاده‌سازی شده — دستورات خام (ریست، برش کاغذ، بولد، دو-برابر-ارتفاع، چیدمان وسط/چپ) مستقیماً به‌صورت بایت ساخته و از طریق سوکت شبکه یا فایل دستگاهِ USB به چاپگر فرستاده می‌شوند.

### متن فارسی روی چاپگر حرارتی
چون اکثر چاپگرهای حرارتی از فونت/کدپیج داخلی خودشان استفاده می‌کنند و هیچ استاندارد یکسانی بین برندهای مختلف برای نمایش صحیح حروف فارسی/عربی وجود ندارد، **شماره‌ی جدول کدپیج فارسیِ مخصوص هر چاپگر** به‌صورت جداگانه در تنظیمات همان چاپگر قابل‌تعریف است؛ متن فارسی پیش از ارسال، به همان کدپیج مشخص‌شده تبدیل می‌شود. یعنی شکل صحیح حروف (اتصال حروف، جهت راست‌به‌چپ) به فریمور خودِ چاپگر سپرده می‌شود — دقیقاً همان روشی که در عمل بین چاپگرهای حرارتی فارسی رایج است.

### مسیردهی چاپ (Print Routing)
برای هر نوع سند (رسید مشتری، دستور آشپزخانه، دستور بار، فاکتور) می‌توان یک یا چند «مسیر» تعریف کرد: یک مسیر عمومی (همه‌چیز به یک چاپگر) یا مسیرهای اختصاصی بر اساس دسته‌بندی محصول (مثلاً اقلام نوشیدنی به چاپگر بار، اقلام غذا به چاپگر آشپزخانه — هرکدام دستور جداگانه‌ی خودشان را می‌گیرند، فقط شامل اقلام همان دسته). اگر برای یک دسته هیچ مسیر اختصاصی تعریف نشده باشد ولی یک مسیر عمومی وجود داشته باشد، کل سفارش به همان چاپگر عمومی می‌رود.

### صف چاپ و تحمل خطا
هر دستور چاپ ابتدا در صف کارهای پس‌زمینه (queue) قرار می‌گیرد، نه مستقیم و بلادرنگ — یعنی اگر چاپگر لحظه‌ای خاموش یا غیرقابل‌دسترس باشد، ثبت سفارش هرگز کند یا ناموفق نمی‌شود. هر تلاش چاپ ثبت می‌شود (در انتظار / ارسال‌شده / ناموفق)، با شمارنده‌ی تلاش مجدد؛ بعد از چند بار شکست، کارکنان مطلع می‌شوند.

### زمان صدور خودکار
دستور چاپ آشپزخانه/بار خودکار وقتی سفارش «تأیید» می‌شود صادر می‌شود (بخش ۷)؛ رسید/فاکتور مشتری با دکمه‌ی دستی «چاپ» از POS یا صفحه‌ی سفارش.

> **نکته برای بهره‌بردار:** این پیاده‌سازی در محیط توسعه با چاپگر واقعی تست نشده (چون سخت‌افزار در دسترس نبوده) — منطق مسیردهی/صف/تلاش‌مجدد کاملاً تست‌شده، ولی صحت نهاییِ اتصال شبکه/USB و خوانایی چاپ فارسی روی هر چاپگر خاص باید قبل از استفاده‌ی واقعی توسط خودِ بهره‌بردار بررسی شود.

## ۱۸. صدا کردن گارسون

یکی از قابلیت‌های متمایز این سیستم است:

- مشتری از صفحه‌ی منو با یک دکمه گارسون را صدا می‌زند — این درخواست فقط برای همان میزی ثبت می‌شود که مشتری اسکن کرده (غیرقابل جعل).
- اگر همان میز از قبل یک درخواست «در انتظار» داشته باشد، درخواست تکراری ساخته نمی‌شود (جلوگیری از انبوه درخواست در اثر چند بار زدن دکمه).
- **آلارم واقعی، نه یک بوق ساده:** برخلاف سایر اعلان‌ها (که فقط یک صدای کوتاه پخش می‌کنند)، صدا کردن گارسون یک **بنر قرمز ثابت در بالای صفحه‌ی پنل ادمین** نشان می‌دهد که نام میز را اعلام می‌کند، همراه با یک **صدای دوتُنی و جدی‌تر** که هر ۲.۸ ثانیه یک‌بار، تا حداکثر ۲۰ بار (حدود ۵۶ ثانیه) تکرار می‌شود و بعد خودش قطع می‌شود.
- این بنر تا وقتی کارمند دکمه‌ی «بی‌صدا کردن» را نزند یا وارد صفحه‌ی صدا کردن گارسون نشود، محو نمی‌شود — برخلاف toastهای معمولی که خودشان بعد از چند ثانیه ناپدید می‌شوند.
- اگر همزمان چند میز گارسون صدا بزنند، همه در همان یک بنر جمع می‌شوند («۳ میز در انتظار گارسون هستند»).
- از پنل ادمین می‌توان لیست درخواست‌ها را دید و هرکدام را «رسیدگی‌شده» علامت زد (این کار به‌صورت آنی/AJAX انجام می‌شود، بدون رفرش صفحه).

## ۱۹. اعلان‌های لحظه‌ای (Reverb)

سیستم از **Laravel Reverb** (سرور وب‌سوکت اختصاصی، سازگار با پروتکل Pusher) برای ارتباط لحظه‌ای استفاده می‌کند — نیازی به سرویس بیرونی (مثل Pusher.com) نیست، همه‌چیز روی سرور خودتان اجرا می‌شود.

### چه چیزهایی لحظه‌ای اطلاع داده می‌شوند
- **ثبت سفارش جدید** (از هر دو مسیر عمومی و POS) → به همه‌ی کارکنانی که دسترسی مشاهده‌ی سفارش دارند.
- **تغییر وضعیت سفارش** → هم به پنل ادمین (از جمله نمایشگر آشپزخانه)، هم به صفحه‌ی پیگیری سفارش مشتری.
- **افزوده‌شدن قلم به سفارش موجود** → به همان کانالِ سفارش.
- **کمبود موجودی انبار** → به کاربران دارای دسترسی مشاهده‌ی انبار.
- **صدا کردن گارسون** → مطابق بخش قبل.

### وابستگی مهم برای اجرا
برای فعال بودن این قابلیت، **دو پردازش باید همیشه در پس‌زمینه اجرا باشند**: `php artisan queue:work` (پردازش صف کارها — همچنین همین صف مسئول ارسال دستورات چاپ حرارتی است) و `php artisan reverb:start` (سرور وب‌سوکت). این دو با اجرای ساده‌ی سایت بالا نمی‌آیند و باید جداگانه (با systemd یا Supervisor — فایل‌های آماده در پوشه‌ی `deploy/` موجودند) دائم در حال اجرا نگه داشته شوند.

## ۲۰. گزارش‌ها و تحلیل‌ها

از پنل ادمین (`گزارش‌ها`)، با انتخاب بازه‌ی تاریخ:

1. **فروش روزانه** — جمع فروش و تعداد سفارش هر روز
2. **پرفروش‌ترین محصولات** — تعداد فروش و درآمد هر محصول
3. **فروش بر اساس دسته‌بندی**
4. **فروش هر میز**
5. **خلاصه‌ی پرداخت‌ها** — جمع مبلغ و تعداد به تفکیک روش پرداخت و وضعیت
6. **عملکرد کارکنان** — تعداد سفارش و درآمد به‌ازای هر گارسون (از سفارش‌های POS)، حجم پرداخت ثبت‌شده به‌ازای هر کارمند، و تاریخچه‌ی کسری/اضافه‌ی صندوق هر شیفت
7. **تحلیل انبار** — ارزش ریالی موجودی فعلی، جمع هزینه‌ی ضایعات، تعداد کالاهای کمبود، خرید به تفکیک تأمین‌کننده/بازه
8. **تحلیل مشتری** — بر پایه‌ی همان آمار زنده‌ی بخش ۶
9. **حاشیه سود و بهای تمام‌شده‌ی کالای فروخته‌شده (COGS)** — **فقط برای مالک** (`reports.profit.view`): برای هر قلم فروخته‌شده، بهای تمام‌شده از حاصل‌ضرب مقدار مصرفی رسپی در میانگین قیمت تمام‌شده‌ی هر ماده محاسبه و از قیمت فروش کم می‌شود. محصولی که هیچ رسپی‌ای برایش تعریف نشده، به‌صراحت «بدون داده‌ی هزینه» علامت می‌خورد، نه اینکه به‌اشتباه با ۱۰۰٪ حاشیه سود گزارش شود.

سفارش‌های لغوشده یا ردشده در همه‌ی این گزارش‌ها نادیده گرفته می‌شوند (فقط فروش واقعی حساب می‌شود).

داشبورد اصلی هم به‌صورت خلاصه: فروش امروز، تعداد سفارش امروز، میانگین ارزش سفارش، تعداد سفارش‌های درحال‌انجام، و ۵ محصول پرفروش امروز را نشان می‌دهد.

**تقویم شمسی:** تمام تاریخ‌هایی که در گزارش‌ها نمایش داده می‌شوند، وقتی زبان سیستم فارسی باشد، خودکار به شمسی (با نام ماه‌های فارسی) تبدیل می‌شوند — بدون نیاز به هیچ افزونه‌ی خارجی PHP.

## ۲۱. لاگ رویدادها (Audit Log)

هر اتفاق مهم و حساس در سیستم ثبت می‌شود: چه کسی، چه کاری، روی چه چیزی، چه زمانی، از چه IP و مرورگری. از جمله (فهرست نمونه، نه کامل):

- ورود موفق/ناموفق، ورود مسدودشده (حساب غیرفعال)، خروج
- ساخت/ویرایش کاربر، تغییر نقش، فعال/غیرفعال کردن حساب
- ساخت/ویرایش/حذف محصول، تخفیف، کالای انبار، تأمین‌کننده
- تغییر وضعیت سفارش، لغو سفارش، رد سفارش، افزودن قلم به سفارش
- ثبت پرداخت، تغییر وضعیت پرداخت، **استرداد وجه**
- ثبت خرید، دریافت خرید، تعدیل/ضایعات/انبارگردانی انبار
- باز/بستن شیفت، ثبت گردش نقدی
- خرج امتیاز وفاداری
- صدور فاکتور
- رسیدگی به درخواست گارسون
- تغییر تنظیمات کسب‌وکار یا سیستم (فقط نام فیلد تغییریافته ثبت می‌شود، هرگز مقدار رمزهای درگاه پرداخت)

این لاگ از پنل ادمین با امکان فیلتر بر اساس نوع عملیات قابل مشاهده است.

## ۲۲. چندزبانگی و راست‌چین

- سیستم به‌طور کامل **دوزبانه** است: فارسی و انگلیسی، با مجموعه‌ای کاملاً موازی از فایل‌های ترجمه برای هر دو زبان — از جمله تمام دامنه‌های جدید (مشتری، تخفیف، وفاداری، انبار، شیفت، فاکتور، چاپ).
- **راست‌چین (RTL)** به‌صورت خودکار برای زبان فارسی فعال می‌شود.
- زبان از سه منبع به ترتیب اولویت تعیین می‌شود: انتخاب دستی کاربر → زبان پیش‌فرض کسب‌وکار → زبان پیش‌فرض کلی سیستم.
- سوییچ زبان از یک دراپ‌داون در هدر (هم در منوی عمومی، هم در پنل ادمین) در دسترس است.

## ۲۳. حالت روشن و تاریک

- هم در منوی عمومی مشتری، هم در پنل مدیریت، حالت تاریک به‌طور کامل پیاده‌سازی شده.
- انتخاب کاربر در مرورگرش ذخیره می‌شود و در بازدیدهای بعدی حفظ می‌شود.
- تعویض حالت آنی است، بدون چشمک زدن یا بارگذاری مجدد صفحه.
- رنگ اصلی و رنگ ثانویه‌ی برند در هر دو حالت روشن و تاریک به‌درستی اعمال می‌شود.

## ۲۴. تنظیمات کسب‌وکار و سیستم

### تنظیمات کسب‌وکار
- نام، ایمیل، تلفن، آدرس
- واحد پول و تعداد رقم اعشار آن (تنظیم روی «صفر رقم اعشار» پیش‌نیاز فعال شدن درگاه‌های ایرانی است)
- زبان و منطقه‌ی زمانی پیش‌فرض
- مالیات (فعال/غیرفعال + نرخ) و عوارض خدمت (فعال/غیرفعال + نرخ)
- رنگ اصلی و رنگ ثانویه‌ی برند
- شبکه‌های اجتماعی
- ساعات کاری هفتگی
- کدام نوع سفارش‌ها پذیرفته می‌شود و آیا پرداخت نقدی هنگام دریافت حضوری مجاز است
- کدام درگاه‌های پرداخت آنلاین فعال باشند (اطلاعات اتصال رمزنگاری‌شده ذخیره می‌شود)
- آستانه‌ی زمانیِ «معطل‌ماندن» سفارش در نمایشگر آشپزخانه (بخش ۱۲)
- لوگوی کسب‌وکار

### تنظیمات سیستم
- تعداد ردیف نمایش‌داده‌شده در هر صفحه از لیست‌ها (صفحه‌بندی)

## ۲۵. ویزارد نصب

نصب سیستم از طریق یک ویزارد مرورگری چندمرحله‌ای انجام می‌شود:

۱. **بررسی پیش‌نیازها** — نسخه‌ی PHP، اکستنشن‌های لازم، دسترسی نوشتن روی پوشه‌های ضروری، قابل‌نوشتن‌بودن فایل `.env`
۲. **اتصال دیتابیس** — تست اتصال و ذخیره در `.env`
۳. **اجرای مایگریشن** — ساخت جدول‌های دیتابیس و بارگذاری نقش‌ها/دسترسی‌های پایه
۴. **ساخت حساب مدیر اصلی (Owner)** — فقط یک‌بار قابل انجام است
۵. **اطلاعات کسب‌وکار** — نام، واحد پول، زبان، منطقه‌ی زمانی
۶. **تکمیل نصب** — به‌صورت خودکار حالت توسعه را خاموش می‌کند و یک قفل نصب می‌گذارد تا ویزارد دیگر هرگز روی یک سایت زنده دوباره قابل اجرا نباشد.

توجه: ویزارد نصب فقط ساختار پایه (نقش‌ها/دسترسی‌ها) را می‌سازد، هیچ داده‌ی نمونه‌ای (بخش ۲۹) در نصب واقعی مشتری اجرا نمی‌شود.

---

## ۲۶. امنیت

- **محدودیت نرخ درخواست:** ثبت سفارش، پیگیری سفارش، صدا کردن گارسون — همه بر اساس IP.
- **محدودیت ورود:** بعد از چند تلاش ناموفق ورود، ورود موقتاً قفل می‌شود.
- **هدرهای امنیتی HTTP.**
- **کدهای QR و شناسه‌ی سفارش/فاکتور:** رشته‌های تصادفی طولانی، غیرقابل‌حدس.
- **پرداخت‌ها:** اطلاعات درگاه پرداخت رمزنگاری‌شده در دیتابیس ذخیره می‌شود.
- **حساب‌های غیرفعال:** ورود با حساب غیرفعال‌شده بلافاصله مسدود می‌شود.
- **آخرین مدیر:** سیستم اجازه نمی‌دهد آخرین حساب فعال با نقش Owner غیرفعال شود.
- **تفکیک سطح اعتماد:** دسترسی‌های حساس (نویسندگی تخفیف، استرداد وجه، عبور اضطراری از موجودی منفی، مشاهده‌ی حاشیه سود، بستن اجباری شیفت دیگران) عمداً از دسترسی‌های عملیاتی روزمره (اعمال تخفیف، ثبت پرداخت، ثبت خرید) جدا شده‌اند.

---

## ۲۷. مدیریت کارکنان

از پنل ادمین می‌توان:
- لیست کامل کارکنان را دید
- کارمند جدید ساخت (نام، ایمیل، رمز عبور، نقش)
- اطلاعات و نقش کارمند را ویرایش کرد
- حساب کارمند را فعال/غیرفعال کرد

کارکنانی که دسترسی داشبورد ندارند (مثل آشپزخانه یا باریستا)، بعد از ورود مستقیم به صف سفارش‌ها/نمایشگر آشپزخانه هدایت می‌شوند، نه داشبورد آماری.

## ۲۸. پشتیبان‌گیری و بازیابی

دو فرمان خط‌فرمان، بدون هیچ وابستگی بیرونی جدید:

```bash
php artisan app:backup                          # می‌سازد: storage/app/backups/cafe-backup-<تاریخ>.tar.gz
php artisan app:restore path/to/backup.tar.gz   # مخرب است — بدون --force از کاربر تأیید می‌گیرد
```

هر پشتیبان شامل یک `mysqldump` کامل از دیتابیس به‌همراه یک نسخه از `storage/app/public` (تصاویر محصول/دسته‌بندی/لوگو) است. نیازمند وجود ابزارهای خط‌فرمان `mysql`/`mysqldump` روی سرور است و فقط از اتصال‌های `mysql`/`mariadb` پشتیبانی می‌کند (نه SQLite تست).

**نکته‌ی امنیتی مهم:** فایل `.env` عمداً داخل پشتیبان قرار نمی‌گیرد — چون رمز `APP_KEY` باید جداگانه و امن نگهداری شود؛ بدون آن، ستون‌های رمزنگاری‌شده (مثل اطلاعات اتصال درگاه پرداخت) بعد از بازیابی قابل خواندن نخواهند بود.

توصیه می‌شود `app:backup` به‌صورت یک کار زمان‌بندی‌شده‌ی روزانه (cron) اجرا و فایل خروجی به خارج از سرور منتقل شود.

## ۲۹. داده‌های نمونه (دمو)

برای آزمایش و نمایش کامل سیستم، یک بسته‌ی داده‌ی نمونه‌ی واقع‌گرایانه با نام «کافه بامداد» آماده است (فقط برای محیط توسعه/دمو — نصب واقعی مشتری فقط نقش‌ها/دسترسی‌های پایه را می‌سازد، هیچ‌کدام از این داده‌ها را اجرا نمی‌کند):

- تنظیمات کامل کسب‌وکار به زبان فارسی، واحد پول تومان، مالیات ۹٪ فعال
- ۵ کارمند نمونه (یک نفر برای هر نقش) + یک حساب Owner آزمایشی
- ۳ بخش سالن و ۱۶ میز
- ۶ دسته‌بندی و ۱۹ محصول واقعی با قیمت، تخفیف و برچسب، به‌همراه گروه‌های افزودنی (سایز، افزودنی‌ها) روی چند محصول
- ۳ مشتری نمونه، یکی عضو گروه «مشتریان ویژه»
- ۳ قانون تخفیف (۱۰٪ تخفیف کل سفارش در قالب یک کمپین، «قهوه سوم رایگان»، تخفیف مبلغ ثابت ویژه‌ی اعضا) و یک کمپین فعال
- ۲ قانون کسب امتیاز و ۲ جایزه‌ی قابل‌خرج (تخفیف درصدی، محصول رایگان)
- ۵ واحد اندازه‌گیری، ۶ کالای انبار با موجودی ابتدایی، و نسخه‌ی مصرف مواد اولیه روی محصولات بر پایه‌ی قهوه (اسپرسو، آمریکانو، لاته، کاپوچینو، موکا، کارامل ماکیاتو)
- یک تأمین‌کننده و یک خریدِ کاملاً دریافت‌شده (برای داشتن میانگین قیمت تمام‌شده‌ی واقعی روی دانه قهوه)
- یک شیفت باز برای صندوق‌دار
- ۲ چاپگر (آشپزخانه و صندوق) و یک مسیر چاپ پیش‌فرض برای دستور آشپزخانه، به‌همراه یک قالب فاکتور پیش‌فرض
- چند سفارش نمونه در وضعیت‌های مختلف: یک سفارش تکمیل‌شده و پرداخت‌شده (که امتیاز وفاداری هم برایش محاسبه شده)، یک سفارش بیرون‌بر در انتظار و پرداخت‌نشده، و یک سفارش تأییدشده و پرداخت‌شده برای مشتری ویژه

## ۳۰. استقرار روی سرور

### پیش‌نیازهای سرور
- PHP نسخه‌ی ۸.۲ تا ۸.۵
- MySQL 8+ یا MariaDB 10.6+
- Composer نسخه‌ی ۲
- Node.js نسخه‌ی ۱۸+ (فقط برای ساخت فایل‌های فرانت‌اند)

### فایل‌های آماده برای استقرار حرفه‌ای
داخل پوشه‌ی `deploy/`:
- تعریف‌های **systemd** برای اجرای دائم صف کارها و سرور Reverb
- تعریف معادل برای **Supervisor**
- یک نمونه‌ی کامل تنظیمات **Nginx** (شامل مسیردهی صحیح به پوشه‌ی `public/` و پراکسی وب‌سوکت برای Reverb)

### نکات مهم استقرار
- ریشه‌ی وب‌سرور (Document Root) باید به پوشه‌ی `public/` اشاره کند — یا در صورت عدم دسترسی به این تنظیم، فایل `.htaccess` آماده‌ی پروژه همین کار را جایگزین انجام می‌دهد.
- بعد از هر استقرار باید `php artisan storage:link` یک‌بار اجرا شود.
- صف کارها و سرور Reverb باید همیشه در پس‌زمینه در حال اجرا باشند، نه با دستور ساده‌ی `php artisan serve`.
- اگر چاپگر حرارتی شبکه‌ای استفاده می‌شود، باید در همان شبکه‌ی محلی سرور (LAN) قابل‌دسترس باشد.
- برای پشتیبان‌گیری منظم، بخش ۲۸ را ببینید.
